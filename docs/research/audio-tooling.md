# Audio tooling: capture, transcription, playback, and Discord

Retrieved **2026-10-28** from primary documentation/source. Research only; no application changes or local ThreadDeck/Kimaki pipeline investigation. “Latest” docs and `main` source are moving targets, not a claim about the versions installed here.

## Main conclusion

Keep **record an audio attachment**, **dictate text**, and **play an attachment** separate. TanStack AI now has an actual browser recorder as well as transcription APIs. AI Elements/shadcn speech-input is primarily dictation UI, not a general-purpose voice-message recorder. Ordinary Discord attachments are much simpler than Discord's special voice-message presentation.

## Verified capabilities and API names

| Tool | Records microphone bytes? | Speech-to-text? | Playback? |
| --- | --- | --- | --- |
| TanStack AI `useAudioRecorder` | Yes: wraps `getUserMedia` + `MediaRecorder`; returns native browser bytes | No, compose with transcription | No player UI; docs preview with native `<audio controls>` |
| TanStack AI `generateTranscription` / `useTranscription` | No; consumes audio | Yes, via a provider adapter/server route | No |
| AI Elements / shadcn.io `SpeechInput` | Only its MediaRecorder fallback exposes a blob callback | Main purpose; browser SpeechRecognition or your transcription callback | No |
| AI Elements `AudioPlayer` | No | No | Yes; media-chrome controls around an audio element |

### TanStack AI

- Import `useAudioRecorder` from `@tanstack/ai-react`. Verified members: `start(): Promise<void>`, `stop(): Promise<AudioRecording>`, `cancel()`, `isRecording`, `isSupported`, `recording`. Options include `audio`, preferred `mimeType`, `onError`, and async-capable `onComplete` (whose returned value can replace the raw recording). `AudioRecording` contains `blob`, `base64`, `mimeType`, `durationMs`, and a TanStack chat `part`. **No transcoding**: recording may be WebM/Opus or MP4, depending on browser. Preferred MIME types are checked with `MediaRecorder.isTypeSupported`; unsupported preferences fall back to the browser default. [Docs](https://tanstack.com/ai/latest/docs/media/audio-recording), [core source](https://github.com/TanStack/ai/blob/main/packages/ai-client/src/audio-recorder.ts), [React source](https://github.com/TanStack/ai/blob/main/packages/ai-react/src/use-audio-recorder.ts).
- Server transcription example is `generateTranscription({ adapter: openaiTranscription('gpt-4o-transcribe'), audio })`, imported from `@tanstack/ai` and `@tanstack/ai-openai`. Server input accepts `File`, `Blob`, `ArrayBuffer`, base64 or a data URL. React `useTranscription` uses a server connection; its JSON audio input must be a string. Results include `text` and optionally language/duration/segments/word timestamps. Provider credentials belong on the server. [Transcription docs](https://tanstack.com/ai/latest/docs/media/transcription).
- Preserve the real MIME type: TanStack's OpenAI/Groq adapters treat **plain base64 as `audio/mpeg`**. For browser WebM/MP4, use a correctly typed data URL (docs strip `;codecs=...` when preparing it), or a typed file/blob on the server. `rec.part` works only with a chat model accepting audio; it is **not** a Discord attachment upload contract. [Recording docs](https://tanstack.com/ai/latest/docs/media/audio-recording).

### What “ChatCN” probably means

- No authoritative audio component library named **ChatCN** was identified in exact-name searches. This is an unresolved name, not proof that no such project exists. The likely reference is **shadcn/ui**, **AI Elements**, or independent **shadcn.io**; ask for the user's URL before selecting a package. Official shadcn documents [AI Elements](https://ui.shadcn.com/docs/ai-elements); shadcn.io explicitly identifies itself as independent on its [Speech Input page](https://www.shadcn.io/ui/speech-input).
- `SpeechInput` has `onTranscriptionChange?: (text: string) => void`, `onAudioRecorded?: (audioBlob: Blob) => Promise<string>`, and `lang`. It prefers browser `SpeechRecognition`/`webkitSpeechRecognition`; otherwise its recorder fallback passes a blob to **your** external transcription service, then emits the returned text. Without that callback the fallback is disabled. It does not promise to return an audio clip in the SpeechRecognition path, so it is the wrong abstraction when every recording must become an attachment. [AI Elements docs](https://elements.ai-sdk.dev/components/speech-input), [source](https://github.com/vercel/ai-elements/blob/main/packages/elements/src/speech-input.tsx), [shadcn.io variant](https://www.shadcn.io/ui/speech-input).
- Important source caveat: current AI Elements source constructs `new MediaRecorder(stream)` without selecting a format, then labels collected bytes `audio/webm`. That label does **not** transcode the browser's output. Do not copy this format assumption into an upload pipeline. Its docs also classify Safari differently from shadcn.io's newer page: feature-detect and test, rather than relying on either browser table. [Source](https://github.com/vercel/ai-elements/blob/main/packages/elements/src/speech-input.tsx).
- `AudioPlayer`, `AudioPlayerElement`, play/seek/time/volume components provide playback. `AudioPlayerElement` accepts `src` or AI SDK `SpeechResult["audio"]` data. Use `src` for an attachment URL or recording preview; no Vercel generation backend is required for ordinary URL playback. [AI Elements player docs](https://elements.ai-sdk.dev/components/audio-player), [shadcn.io player](https://www.shadcn.io/ui/audio-player).

## Browser and Electron constraints

- `navigator.mediaDevices.getUserMedia({ audio: true })` acquires a stream, not a recording or transcript. It requires a secure context and microphone authorization; embedding/Permissions Policy can block access. Permission denial, missing devices, and hardware/OS failures need UI handling. Stop the stream's tracks when finished/cancelled/unmounted. [W3C capture specification](https://w3c.github.io/mediacapture-main/).
- `MediaRecorder` emits encoded `Blob` data through `dataavailable`; finalize after stopping. Probe `MediaRecorder.isTypeSupported(type)` and retain the actual `recorder.mimeType`; explicitly requesting an unsupported native format can throw `NotSupportedError`. Renaming `.webm` to `.ogg` or changing Blob MIME metadata does not convert containers/codecs. [W3C recording specification](https://w3c.github.io/mediacapture-record/).
- Playback needs a decoder supported by the actual browser/Electron build. `<audio controls src=...>` is sufficient for a first player; `canPlayType()` is a capability hint, not proof a particular file will decode. Handle `play()` rejection/autoplay restrictions; prefer user-initiated playback. [WHATWG media specification](https://html.spec.whatwg.org/multipage/media.html).
- Electron renderer capture uses the browser APIs, but Electron session and OS permission layers still apply. Handle `media` requests with an origin-scoped `setPermissionRequestHandler` and corresponding `setPermissionCheckHandler`; inspect requested media types rather than granting every permission. [Electron session source/docs](https://github.com/electron/electron/blob/main/docs/api/session.md#sessetpermissionrequesthandlerhandler).
- macOS requires microphone consent and `NSMicrophoneUsageDescription` in the app's `Info.plist`; `systemPreferences.askForMediaAccess('microphone')` is macOS-only. `getMediaAccessStatus('microphone')` exists on macOS/Windows; Windows global privacy settings can deny desktop microphone access. Do not assume that Chromium/Electron implies Chrome's hosted SpeechRecognition service works. Validate recording and dictation separately in the packaged app. [Electron systemPreferences docs](https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos).

## Discord: ordinary attachment versus voice message

**Ordinary file:** Create Message supports multipart `files[n]` plus `payload_json`; attachment metadata IDs match the file indexes. Use a truthful filename, content type, and raw bytes. No voice-message flag, waveform, or voice-specific duration metadata is required. The generic upload contract does not publish an audio-codec whitelist: MP3, WAV, OGG/Opus, WebM/Opus, and M4A/MP4 are candidate file attachments, **not a verified promise of inline playback across Discord clients or downstream transcription**. Generic file upload, Discord playback, browser playback, and transcription-provider acceptance are different capabilities. [Upload contract](https://docs.discord.com/developers/reference#uploading-files), [Create Message](https://docs.discord.com/developers/resources/message#create-message).

**Special voice message:** Set `IS_VOICE_MESSAGE` (`1 << 13`, 8192). Exactly one audio attachment; no text content/stickers/etc.; message cannot be edited. Supply attachment `duration_secs` and base64 `waveform`; the uploaded attachment Content-Type must begin `audio/`. Waveform is one byte per sample, at most 256 samples (clients sample at most once per 100 ms, downsampling longer clips). Discord documents its clients uploading mono 48 kHz, 32 kbps Opus in OGG **as of 2023-04-14**, expressly calling encoding/waveform details changeable implementation details—not a timeless universal requirement. Browser-native WebM is not OGG: special voice presentation may require remuxing/transcoding and compatibility testing. [Voice-message contract](https://docs.discord.com/developers/resources/message#voice-messages), [required attachment metadata](https://docs.discord.com/developers/resources/message#attachment-object-attachment-request-structure).

**Limits:** Retrieved upload docs say **20 MiB default per file**, potentially higher with entitlement/server context; retrieved Create Message docs separately cap the **whole request at 25 MiB**. Apply the relevant endpoint/context limits and handle rejection; do not hardcode an older 8/10 MiB assumption. [Upload limits](https://docs.discord.com/developers/reference#uploading-files), [Create Message](https://docs.discord.com/developers/resources/message#create-message).

## Recommendation and remaining uncertainties

For an attachment-first prototype, use native MediaRecorder or the verified TanStack recorder, preview with `<audio>` or AI Elements' URL player, and upload an **ordinary audio attachment**. Add transcription only if dictated text is wanted; reuse an existing server-side transcription path if available. Do not adopt a second AI chat stack solely for a record button.
